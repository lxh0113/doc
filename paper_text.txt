基于协同编辑和AI辅助的智能云笔记系统
摘  要
现在信息越来越多，个人怎么整理知识、团队怎么一起协作，都变得越来越复杂。但市面上主流的笔记软件，要么同步慢，多个人一起编辑时容易乱，要么智能辅助功能很鸡肋。针对这几个问题，我们做了一套智能知识管理平台——底层是云端笔记，外面包了一层知识社群的功能。这个平台的核心思路是：先用笔记帮个人管好知识，再让团队能一起写东西，最后让知识在社群里流动起来。技术上我们融合了常见的Web开发方式、CRDT这种多人协同的数据同步方法，还有大模型的语义理解能力，希望做出一个功能全、用起来也顺手的云端知识工具。
工程上我们严格做了前后端分离。前端用React 18 + TypeScript，TypeScript的好处是在写代码阶段就能帮忙发现很多类型错误。后端是Spring Boot，暴露的是RESTful接口。
AI功能的接入方式我们区分了两种情况：
像文本校对、润色、翻译这种需要完整处理而且内容比较敏感的操作，我们走了一个Python Flask写的微服务网关，由它转发出去。
段落扩写、生成摘要这种要流式返回的场景，前端直接通过SSE（Server-Sent Events）连第三方接口，不经过中间层，这样延迟更低。
多人协同编辑这块，我们用了Yjs这个开源的CRDT实现。它里面的YATA算法会给每个字符一个全局唯一的ID，多人同时插入或删除时，通过确定性的排序规则最终能保证所有人看到的内容一致。再配合y-websocket，不同用户的编辑操作在几毫秒内就能广播并合并完。
我们还做了一个版本快照表，每次编辑都能生成一个可追溯的时间点，方便后面回溯历史版本。
AI能力这边，我们接的是讯飞的中文拼写校对接口和Elysia Tools的语义加工接口，最终提供了校对、润色、翻译、扩写、摘要这五种文本处理功能。
目前系统已经实现了几个核心功能：
用栏目和标签组织文章
文章从草稿到归档的完整生命周期
用户的社交关系维护
基于CRDT的多人实时协同写作
大模型驱动的语义辅助写作
基于协同过滤的个性化内容推荐
我们用Apache JMeter模拟了100个用户同时使用的情况做性能测试。结果是这样的：
核心接口的平均响应时间控制在250毫秒以内
协同编辑的端到端同步延迟中位数在50毫秒以下
这说明，不管是个人记笔记，还是中小团队一起写文档，这个系统的性能都是可用的。
这个项目从前端交互到底层数据一致性，我们算踩了一遍完整的坑，也沉淀了一套可行的技术方案。对于云笔记这类工具来说，算是提供了一种从“存储工具”往“认知伙伴”演化的参考实现。

Intelligent Cloud Note System Based on Collaborative Editing and AI Assistance
Abstract
Nowadays, there is more and more information, and it's becoming increasingly complicated for individuals to organize their knowledge and for teams to collaborate with each other. However, most mainstream notetaking software either has slow synchronization, gets messy when multiple people edit together, or comes with AI assistance that feels quite useless. To address these problems, we built an intelligent knowledge management platform — with cloud notes as its foundation and community features wrapped around it. The core idea of this platform is: first, help individuals manage their knowledge with notes; second, enable teams to write together; and finally, let knowledge flow across communities. Technically, we combined common web development practices, CRDT (a data synchronization method for multiperson collaboration), and the semantic understanding ability of large language models, hoping to create a cloudbased knowledge tool that is featurerich and smooth to use.
On the engineering side, we strictly followed a frontend and backend separation approach. The front end uses React 18 and TypeScript — the benefit of TypeScript is that it helps catch many type errors at the coding stage. The back end is Spring Boot, exposing RESTful APIs.
We used different routing strategies for AI feature integration. For operations that require full processing and involve sensitive content — such as text proofreading, polishing, and translation — we built a Python Flask microservice gateway to forward requests. For streaming scenarios, like paragraph expansion and summarization, the front end connects directly to thirdparty interfaces via SSE (ServerSent Events), bypassing the intermediate layer, which results in lower latency.
For multiperson collaborative editing, we used Yjs, an opensource CRDT implementation. Its YATA algorithm assigns a globally unique ID to each character. When multiple people insert or delete content at the same time, deterministic ordering rules ensure that everyone eventually sees the same consistent document. With ywebsocket, editing operations from different users are broadcast and merged within just a few milliseconds.
We also built a version snapshot table, so that every edit generates a traceable point in time, making it easy to go back and review previous versions later.
For AI capabilities, we integrated iFlytek's Chinese spelling correction API and Elysia Tools' semantic processing API, finally providing five text processing functions: proofreading, polishing, translation, expansion, and summarization.
The system has already implemented several core features:
Organizing articles using columns and tags
The full lifecycle of articles from drafting to archiving
Dynamic maintenance of user social relationships
Realtime collaborative writing based on CRDT
Semanticassisted writing driven by large language models
Personalized content recommendation based on collaborative filtering
We used Apache JMeter to simulate 100 concurrent users for performance testing. Here are the results:
The average response time of core APIs stays under 250 milliseconds
The median endtoend sync delay for collaborative editing is below 50 milliseconds
This shows that whether it's personal notetaking or small to mediumsized teams writing documents together, the system's performance is acceptable.
From frontend interaction to bottomlayer data consistency, we basically went through all the typical pitfalls in this project and ended up with a solid set of practical technical solutions. For cloud notetaking tools, this provides a reproducible reference architecture for evolving from a "storage tool" toward a "cognitive partner".
Key words: Cloud Note System; Collaborative Editing; CRDT Algorithm; AI Assistance; Front-end and Back-end Separation; Spring Boot; React
第1章  前  言
1.1  项目背景与意义
1.1.1 项目背景
在大学教学和团队协作中，文档编写和知识沉淀是一个很常见的需求。以软件工程课的需求规格说明书为例：一个五人小组通常采用“分头写、事后合并”的方式——成员A写功能需求，成员B写非功能需求，最后组长手动合并。这种方式看似高效，其实有三个主要问题。
第一，合并时冲突频繁。如果A修改了引言，B基于旧版本写了新内容，最后合并时就可能出现逻辑断裂甚至内容丢失，导致大量重复劳动。
第二，异步沟通的反馈太慢。大家在各自的文档里独立工作，看不到别人的修改意图，逻辑不一致和术语不统一的问题往往到合并时才暴露，改起来成本很高。
第三，文档质量过于依赖个人能力。本科生写技术文档，很容易出现语法错误、表达啰嗦、术语用错等情况。传统笔记软件只是被动存储，不会主动提供语法检查、风格优化或内容摘要等智能帮助。
这些问题的根源，在于传统的中心化锁同步和异步消息机制。近五年来，CRDT理论的成熟和工程化，让去中心化的实时协同编辑变得可行。CRDT利用交换律、结合律和幂等律，从数学上避免了并发编辑的冲突问题，正好解决了版本合并和反馈延迟两大难点。同时，大模型在参数量突破临界点后展现出的上下文推理能力，为语法纠错、风格改写和内容扩写提供了很好的技术支持，弥补了文档质量依赖个人经验这一短板。由此，本课题锚定于CRDT与大语言模型这两条技术脉络的交汇点，试图构建面向下一个十年的智能云笔记系统。
1.1.2 研究开发现状分析
现在市面上的云笔记产品，各家走的路不太一样。
国外这边，Notion 主打的是块编辑 + 关系型数据库，用起来很灵活，大家认可度也高。它的协作功能主要就是异步评论和基础同步，但实时编辑的反应还不够快，没到毫秒级那种程度。Google Docs 用 OT 算法做了业界公认很好的实时协同体验，但它的问题在于知识管理能力比较弱——也就是简单的文档整理，没有太细的分类和检索体系。OneNote 深度绑定了 Office 全家桶，在商业场景里靠着这个生态优势，还是有一批忠实用户。
国内这边，语雀主要服务开发者和企业用户，差异化在于知识库的结构化沉淀。石墨文档主打轻量协同办公，它的 OT 实时同步体验在同类型产品里排得上号。飞书文档嵌在字节的组织协作生态里，文档流转和审批、通知这些工作流节点是紧密连在一起的。
再说协同编辑的底层算法，长期有两条路线并存。
OT 算法历史比较久，理论基础可以追溯到二十多年前的 CSCW（计算机支持的协同工作）研究。像 Google Docs、Office Online 这种亿级用户的产品，都用的是 OT 路线。它的核心逻辑是：当多个并发操作到达服务器时，系统会调用预设的转换函数，把操作里的参数（比如插入位置）重新映射，让它在当前文档状态下仍然语义正确。但 OT 有个很大的工程代价——随着操作类型的增加，需要写的转换函数对呈组合爆炸式增长。比如新增一种操作类型，就要为它和所有已有类型的每一种组合分别写两个函数。在富文本编辑场景里，这个问题尤其突出。
CRDT 走的是另一条路。它不是在操作到达后再去调停冲突，而是在数据结构设计阶段，就把“可交换”“可结合”的合并语义嵌进去，让并发操作先天就是相容的。这种“结构即协议”的思想，不再依赖中心节点做协调，天然支持离线编辑和去中心化部署。像 Figma 这种设计工具已经在生产环境大规模验证了 CRDT 的可行性，Notion 的部分后端同步也转向了这个路线。
最后看智能化辅助。
目前大多数云笔记的 AI 能力还停留在浅层——要么是关键词统计，要么是简单的语种转换。但最近 GPT、文心一言、ChatGLM 这些大模型，在参数规模和推理能力上都跨过了一个门槛。更深层的辅助创作能力正在出现，比如基于上下文的逻辑扩写、特定风格的文体迁移、细粒度的语法纠错、抽取式或生成式摘要——这类高阶的语义计算能力，现在还处在从实验原型向产品落地的早期阶段，云笔记领域的 AI 应用远没有到饱和的程度。
1.1.3 项目的目标和范围
这个毕设的目标挺明确的，就是在系统层面做一套云笔记系统，把协同编辑和 AI 辅助这两块能力真正落地。整体分成三个递进的层次来说。
第一个层次：先把云端笔记的基础功能做完整。
具体来说就是笔记的创建、富文本编辑、多种方式搜索、带权限的分享，这些全生命周期的操作都要支持。在编辑功能上，要能插多媒体文件，能用标签来组织笔记，还能支持全文倒排索引。这一层说白了就是把个人记笔记的基础需求给满足了——能写、能找、能分享给别人。
第二个层次：实现多人实时协同编辑。
我们基于 CRDT 这种去中心化合并的语义来做，用 Yjs 这个框架搭一个多用户并发编辑的无锁同步通道。系统不仅要做到多人的光标位置和选中的文本区域能在毫秒级内广播出去，还要能沿时间轴记录每一次文档状态的快照，并且提供版本回退的功能。
第三个层次：接入大模型驱动的语义辅助。
我们写一个适配层去封装大模型 API，把翻译、扩写段落、润色文体、校对语法、生成摘要这五个智能功能集成到编辑过程中。用户在界面上就是选中一段文字，点一下按钮就能触发。目标是让写东西的效率更高，规范性也更好。
项目的范围，我们主要关注三类场景：个人记笔记、小团队协作（比如几个人一起写一个文档）、以及在社区里分享笔记。目标用户是高校学生、知识工作者，还有十个人以下的小团队。
那些比较复杂的企业级功能，比如复杂的组织权限、安全审计这些，我们这个版本不做。我们把工程精力集中在把核心功能做扎实，以及那两个技术亮点（CRDT 协同、大模型辅助）上做深。

第2章  技术与原理
2.1  CRDT协同编辑算法
2.1.1 协同编辑技术概述
协同编辑，说白了就是不同地方的人通过网络一起编辑同一份文档，系统要保证最后大家看到的内容是一样的。这里面的核心难题是：在没有全局锁协调的情况下，不同用户同时做的修改，合并之后既不能丢内容，也不能出现混乱的情况。
最简单的做法就是加锁。加锁确实能防止冲突，但代价是用户操作会被卡住，这跟实时协同想要的流畅体验正好反着。
学术界和工业界研究了很久，最后走出了两条不同的无锁技术路线：一条叫操作转换（OT），一条叫无冲突复制数据类型（CRDT）。
OT的思路是：冲突来了之后再去解决。服务器维护一个操作历史，当新到的操作跟已经执行的操作在位置上有冲突时，就用预先写好的转换函数，重新算一下操作的位置参数（比如插入位置要向右偏移）。这个方案的问题是强依赖中心服务器，部署不灵活，而且操作类型一多，转换函数的数量会爆炸式增长，工程上很难搞。
CRDT的思路完全不同。它不是在操作层面去“补锅”，而是在设计数据结构的阶段就让冲突根本不会发生。CRDT要求合并操作满足交换律、结合律、幂等律这三条数学性质。交换律意味着同步的顺序不影响最终结果；结合律意味着多节点下合并路径随便怎么走都一样；幂等律意味着同一个更新重复应用也没事。这三条加起来，从数学上直接把冲突问题消灭了。
我们怎么选的？ 系统要在“轻量部署、高并发、低延迟”这三个约束下做权衡。
加锁方案直接放弃，因为阻塞交互太影响体验了。
OT方案虽然成熟，但它需要中心节点，操作转换的组合复杂度也高，在小团队轻量部署的场景下有点杀鸡用牛刀。
CRDT的去中心化合并语义，天然适合“无中心、能离线、自动收敛”的需求。每个客户端本地随便改，同步层只负责把操作传过去，合并的正确性由数据结构本身的数学性质保证。
这种“结构即协议”的思路，让我们最终选了CRDT来做协同编辑引擎。
2.1.2 CRDT算法原理
CRDT是一类设计很巧妙的分布式数据结构。它的核心想法其实不难理解：如果你能让某种数据类型的合并操作在数学上满足半格（Join-Semilattice）的性质，那么多个副本之间的状态能不能收敛，就可以直接由数学来保证，不用再做额外的协调。
具体到操作层面，CRDT允许每个副本在本地上随便写——不需要申请锁，也不用等别人确认。当各个副本通过网络交换各自的状态增量时，合并操作会自动把不一样的状态“抬升”到半格里的最小上界，这样整个系统就会自然收敛到同一个最终状态。
三条公理分别解决了不同方面的不确定性问题：
交换律 merge(a, b) ≡ merge(b, a)：不管谁先谁后，合并结果都一样。A先发给B还是B先发给A，最后状态是一样的。
结合律 merge(a, merge(b, c)) ≡ merge(merge(a, b), c)：不管你按什么路径合并，结果都一样。在多节点互相同步的场景下，最终状态只取决于有哪些操作，跟中间经过谁转发没有关系。
幂等律 merge(a, a) ≡ a：同一个东西合并多次跟合并一次效果一样。这样底层网络用“至少一次”的投递方式（比如TCP重传、Gossip重复扩散）就没问题了，重复应用不会出错。
2.1.3 Yjs库的实现机制
框架选型对比
现在主流的CRDT实现库有三个：Yjs、Automerge和Loro。
Automerge用JSON-like的数据结构，适合结构化数据，但做文本编辑时性能不太行。
Loro是用Rust写的比较新的库，性能很强，但生态还没起来。
Yjs专门为文本协同编辑做了优化，有现成的WebSocket传输层（y-websocket），跟Quill编辑器有官方绑定（y-quill），社区活跃，文档也全。
我们的前端是React+TypeScript，Yjs原生支持JavaScript，npm生态也丰富，所以选它最合适。
Yjs可以说是Web前端生态里工程化做得最好的CRDT库了。它专门为富文本协同编辑场景定制了YATA算法，在并发插入排序和墓碑回收这些关键地方做了大量优化。我们这个系统的协同编辑引擎就选Yjs了。
YATA算法的核心机制
YATA算法的设计可以分成四个互相配合的层次：
全局唯一标识符：Yjs给每个插入的字符分配一个二元组（clientId, clock）。clientId是会话建立时分配的唯一客户端编号，clock是这个客户端上的单调递增逻辑时钟。当两个插入操作同时指向同一个位置时，YATA按标识符的字典序来决定谁先谁后，这样就不会像基于绝对索引的方案那样出现不确定的情况。
相对位置定位：传统编辑器是“在第k个位置插入”这种绝对定位。YATA不一样，它表达成“在id_left这个字符之后、id_right这个字符之前插入”。这种相对定位的方式，让插入操作跟动态变化的索引位置解耦了，就算并发插入了很多字符，每个插入操作的“本意”还是能被准确解析出来。
双向链表结构：Yjs内部用双向链表而不是数组来存文档。每个节点有内容、唯一标识符、以及left/right两个指针。并发插入发生时，YATA在链表里做确定性的有序插入，而不是在数组里做不确定的索引位移，从结构上避免了并发写入的冲突问题。
墓碑机制：删除操作不会真的把节点删掉，而是给它打一个删除标记。保留这些“已删除”的节点作为骨架，这样后面的并发插入还是能准确定位它们的相对参考点——即使参考字符已经被某个副本标记为删除了，它的标识符还在数据结构里，可以给其他副本的并发操作提供稳定的参照。
图2-1 Yjs处理并发冲突图
图2-1是Yjs怎么处理并发冲突的一个例子。假设用户0和用户1，一个在A和B之间插东西，另一个在B和C之间插东西。这两个操作同时发生的时候，Yjs会根据用户的ID来决定哪个操作先执行，最后所有人看到的文档状态是一样的。
协同编辑的时候，Yjs可以用WebSocket或者WebRTC来传操作更新。WebSocket是目前的主流，支持双向通信；WebRTC支持点对点直接连，可以减轻服务器压力。
我们系统选的是WebSocket，走中心化服务器转发操作，这样可靠性和一致性更好。

AI能力分流接入决策分析
我的AI能力接入没有做一个中心化的网关，而是根据三个维度来分流：安全敏感度、延迟要求和负载特征。下面是具体的决策逻辑。
后端代理路径（纠错、润色、翻译）
这三类功能需要把完整的文章正文发给外部模型接口，文本内容比较多，而且涉及用户的核心创作内容。所以安全可控性比低延迟更重要。我通过本地AI代理服务统一管理API密钥、做敏感词过滤、写审计日志，这样密钥泄露的风险就只局限在单个内网节点上。额外增加的一跳网络转发（大概几十毫秒），在同步调用模式下，用户基本感觉不到。
前端直连路径（扩写、总结）
流式生成这种工作负载，跟短请求-响应的同步调用是不一样的。如果让长连接的SSE经过后端中转，服务器要为每条连接占用一个线程或协程资源，数据路径上也多了一次转发延迟。我让前端直接跟Elysia Tools的SSE推理端点连接，这样首Token时间（TTFT）明显缩短，后端也不用去维持那些长连接了。
技术栈选型考量
AI代理层我用了Python（Flask）而不是直接拿Java调，这是比较务实的选择。讯飞开放平台对Python SDK的维护力度，尤其是WebSocket鉴权链路的完整性，比对Java SDK的投入要好很多。另外Python的requests库在处理HTTP流式响应时的缓冲区控制和超时设置，也更符合我这套系统的需求。我的做法是“用最合适的语言做最专业的事”，而不是强求技术栈统一。

前端直连方案因将API密钥暴露于浏览器运行时环境，必然引入额外的攻击面，需逐项辨识风险向量并给出成体系的缓解对策。
系统采用三路径AI接入架构：后端代理路径（纠错、润色、翻译）、前端直连路径（扩写、总结SSE）、前端独立路径（AI小助手WebSocket）。其中前端直连路径将API密钥暴露在前端代码或网络请求中，存在以下安全风险需要逐项论证并给出缓解措施：
风险1：API密钥泄露威胁
前端代码中Elysia Tools的API Key可被任何访问网站的用户通过浏览器  开发者工具查看，存在被恶意第三方提取并滥用的风险。
缓解措施：
1. 在Elysia Tools服务商后台启用域名白名单（CORS Origin限制），使该API Key仅能在本系统授权的域名下调用；
2. 扩写和总结功能不涉及用户  隐私数据（用户完全自愿提交选中文本），即使密钥被滥用也不会导致用户数据泄露；
3. 与用户认证体系解耦：Elysia API Key是平台级密钥，非用户级密钥，滥用不会关联到特定用户身份。
风险2：中间人攻击
前端直连第三方API的HTTPS连接可能被中间人拦截，窃取用户提交的文本内容。
缓解措施：
所有前端直连请求均使用HTTPS加密传输；
扩写与总结功能处理的是用户主动选中的公开可编辑文本，非敏感个人信息；
涉及敏感内容的纠错、润色、翻译等操作全部走后端代理路径。
风险3：前端代码完整性威胁
前端JavaScript代码可被篡改（如浏览器扩展注入），将AI请求重定向到恶意端点。
缓解措施：
生产环境部署时启用SRI校验；
通过CSP头限制可连接的域名白名单；
前端SSE连接域名硬编码为官方elysiatools.com。
综合风险评估
前端直连路径虽然暴露平台级API Key，但结合域名白名单与CSP策略，且处理的是用户主动提交的非敏感文本，整体风险可控。相比之下，该架构在降低后端负载、减少延迟、实现端到端流式传输方面的技术收益更明显。同时，我将纠错、润色、翻译等涉及全文处理的功能统一通过后端代理，确保敏感内容处理路径的安全性。

API密钥安全设计
针对第三方API密钥泄露这个风险，我做了分级防护：
机密级密钥（后端路径）：所有API Key和Secret只存在服务器的环境变量里，通过docker-compose.yml注入，代码仓库里不提交。只有本地AI代理服务能访问这些密钥。
公开级密钥（前端路径）：Elysia Tools的API Key不能走后端代理（走了就会破坏SSE直连的低延迟优势）。我在服务商后台开了域名白名单，这样密钥就算被盗也只有在授权域名下才能调用。
超时与降级策略
前端直连路径：如果SSE连接断了超过3秒，前端会自动提示“AI生成中断，请重试”，并且把已经生成的内容保留下来，不让用户白写。
后端代理路径：调用外部API时，网络连接超时设3秒，请求总超时设5秒。超时后主服务返回一个兜底文案，不会直接抛系统报错。
WebSocket鉴权
协同编辑的y-websocket服务运行在 ws://localhost:1234。我的安全设计如下：
连接建立阶段：客户端将JWT token作为URL参数传递（如 ws://localhost:1234/文档ID?token=xxx），服务端在upgrade阶段验证token有效性。
会话维持阶段：服务端定期校验token是否过期，过期后主动断开连接并返回401。
权限执行：服务端根据token解析用户ID，结合Cooperate_Member表验证用户对文档的权限（owner/edit/view），view权限用户仅能接收更新，不能发送编辑操作。
生产环境增强：部署Nginx反向代理WebSocket，启用WSS协议，确保传输加密。
AI调用限流与缓存
限流设计
用户级限流：每用户每分钟最多调用纠错/润色/翻译各10次、扩写/总结各5次，通过Redis计数器实现滑动窗口限流。超限返回HTTP 429及提示“操作太频繁，请稍后再试”。
IP级限流：未登录状态或异常高频调用时启用IP级别限流，每IP每分钟最多调用AI功能总计20次。
全局限流：保护后端Python AI代理服务，全局QPS限制为50，超出排队的请求最长等待3秒后返回降级响应。
缓存策略
纠错结果缓存：以输入文本的MD5哈希为键，缓存24小时。
翻译结果缓存：以（源语言，目标语言，输入文本MD5）三元组为键，缓存48小时。
润色结果不缓存：润色结果受上下文影响，相同输入可能有不同优化方向。
缓存存储：本地Python服务使用lru_cache加定时过期字典。生产环境建议迁移至Redis，TTL=24h，最大内存500MB，使用allkeys-lru淘汰策略。
缓存命中率监控：通过AI_Call_Log表的cache_hit字段统计各功能缓存命中率，当前预估命中率约35%（主要来自翻译和纠错的重复调用）。
2.3  系统架构技术
2.3.1 前后端分离架构
前后端分离架构已经是现代Web工程中的常见做法。我的理解是：前端负责用户界面和交互展示，后端负责业务逻辑和数据存储，两者之间只通过定义好的HTTP API进行无状态通信，互不干涉对方的实现细节。
表现层技术选型
前端技术选型我主要考虑了三个方面：类型安全、组件化程度和状态管理复杂度。
React 18的函数式组件和Hooks，把UI逻辑封装成可组合的纯函数单元，很大程度上降低了跨组件状态同步的心智负担。TypeScript的静态类型系统在编译阶段就能发现类型不匹配、空值传播这类运行时常见错误，把定位问题的时间从浏览器控制台提前到了写代码的IDE里。Ant Design 5.x组件库提供了一套风格统一、符合无障碍规范的企业级组件，让界面在不需要额外约束的情况下保持视觉一致。
服务层技术选型
后端我选了Spring Boot 3.x作为主体框架。它的“约定优于配置”设计理念，让项目的启动成本比传统的XML配置方式低很多。MyBatis-Plus在MyBatis基础上增加了面向对象的CRUD自动生成层，把我从重复写SQL的麻烦中解放出来。后端暴露的API严格遵循REST风格——用HTTP方法动词表示CRUD操作，用路径中的名词表示资源层级，用状态码传递操作结果——这样能跟前端保持最大程度的契约独立性。
2.3.2 微服务架构设计
针对AI辅助这个子系统，它的技术栈需求和资源消耗跟核心业务不太一样，所以我把它从核心业务单体中拆分出来，作为一个独立部署的微服务。这个AI代理服务用了Python/Flask技术栈，跟Java写的主核心业务服务之间只通过本地HTTP协议交换JSON格式的请求和响应。
这个拆分决策带来了三个好处：
第一，技术栈选择更自由。 AI代理服务可以充分利用Python生态里积淀深厚的HTTP客户端库和机器学习工具链，不用被Java体系的SDK完备度限制住。
第二，弹性伸缩的粒度更精细。 AI推理通常比普通业务CRUD操作消耗更多的CPU和内存资源（差一个数量级以上）。独立部署之后，我可以根据负载信号单独对AI服务做水平扩展，不用为了AI而把整个系统都配成高配，造成资源浪费。
第三，故障隔离更安全。 如果AI服务因为外部API超时或者模型推理异常而宕机，核心的笔记读写、搜索和协作功能仍然在线。故障被严格限制在智能辅助这个增值层内，不会波及主业务。
服务间通信我用了HTTP协议，数据格式是JSON。核心业务服务调用AI辅助功能时，把待处理文本作为请求参数传过去，AI辅助功能调用外部大模型API，把结果返回给核心业务服务，再由核心业务服务返回给前端。

2.4 个性化推荐算法
2.4.1 推荐系统在云笔记平台中的定位
推荐子系统管两个地方的内容推荐：首页信息流和侧边栏“猜你喜欢”。它的任务是从平台公开的文章里，给每个登录用户推荐他可能喜欢的Top-N篇文章。
这看起来是个经典的推荐问题，但在云笔记平台里，有两个互相放大的难题：
冷启动问题：新用户没什么行为数据
新注册的用户基本没干过什么——没点赞、没收藏、没评论，也没怎么停留看文章。这样一来，协同过滤类的推荐模型就不知道用户喜欢什么。这就是推荐系统里常说的“冷启动”。在我的平台里，因为用户写的文章比较专业、分布也比较长尾，这个问题更明显。
实时性和算力的矛盾
计算文章之间相似度的复杂度是O(|U| × |I|²)，|U|是用户数，|I|是文章数。假设十万用户、百万篇文章，每个请求都要实时算推荐列表，计算量远远超过单机甚至小型集群能扛住的水平。我需要在离线算好和在线实时响应之间找一个平衡点。
为了解决这两个问题，我用了“Item-CF + 冷启动时推热门内容 + 定时预计算缓存”这个组合方案。
2.4.2 基于物品的协同过滤算法（Item-CF）
核心思想
Item-CF的基本假设是：如果大多数喜欢文章A的用户也喜欢文章B，那么文章A和文章B是相似的（被同一批用户共同偏好）。基于此，为用户推荐与其历史互动过的文章最相似的其他文章。相比于基于用户的协同过滤（User-CF），Item-CF在物品数量远小于用户数量的场景下计算效率更高，且物品间的相似度比用户间的相似度更稳定（物品属性不会频繁变化）。

计算复杂度分析
设用户数为 |U|、文章数为 |I|。Item-CF的离线计算分为两阶段：
文章相似度矩阵计算：理论复杂度为 O(|U| × |I|²)，但通过只计算有共同互动用户的文章对（稀疏优化），实际复杂度约为 O(|U| × |I| × k)，其中 k 为每篇文章的平均互动用户数，通常 k 远小于 |U|。
推荐列表生成：复杂度为 O(|U| × |I_avg| × N)，其中 |I_avg| 为用户平均互动文章数。
本项目采用定时预计算（每日凌晨2:00）和结果缓存（recommend_result表），将在线请求的计算复杂度降为 O(1)，即直接读取缓存。
2.4.3 冷启动策略
当用户处于以下两种情况之一时，Item-CF因缺乏互动数据而失效，系统切换到基于全局统计的热门推荐策略：
新用户冷启动（注册不足7天或互动次数 < 5）：展示全局热门文章。热门度得分 HotScore 计算方式：
（2.4）
本项目取 HotScore 最高的5篇文章，同时保证这5篇文章来自至少3个不同专栏，避免推荐结果太单一。
新文章冷启动（发布不足24小时）
新发布的文章因为没有互动数据，无法计算相似度。本项目采用“编辑推荐位 + 随机曝光”的策略：新发布的、审核通过的文章会以20%的概率随机插入到活跃用户的推荐列表第3位。具体来说，推荐列表的5篇文章中，前2篇来自Item-CF，第3位随机插入一篇新文章，后2篇继续来自Item-CF。通过这种方式积累初始互动数据。当一篇新文章累计获得至少3次互动后，就正式进入Item-CF的相似度计算池。
冷热切换条件
如果用户注册天数达到7天以上，并且总互动次数达到5次以上，则使用Item-CF推荐；否则使用其他策略（如热门推荐或随机推荐）。
2.4.4 推荐效果离线评估

准确率（Precision@5）：推荐的5篇文章中，用户在测试集上实际产生互动（点赞/收藏/评论）的比例。

覆盖率（Coverage）：被至少推荐过一次的去重文章数占总文章数的比例。衡量推荐系统是否只推荐了少数“头部”热门文章。
（2.6）
多样性（Diversity）：推荐列表内5篇文章两两之间的平均不相似度。值越高说明推荐结果越不单一。

2.4.5 推荐算法的工程实现要点
定时预计算
文章相似度矩阵的计算（也就是遍历所有有共同互动用户的文章对）在每天凌晨2:00通过Spring的@Scheduled定时任务触发。算完之后，更新recommend_result缓存表里所有活跃用户的推荐列表，把expires_at字段设成第二天凌晨2:00。前端请求推荐时先读缓存，只有缓存没命中的时候才会降级走实时计算（不过这时候响应时间会从50毫秒以内涨到大概500到800毫秒）。
增量更新机制
用户在两次定时计算之间新增的互动行为，本项目用滑动窗口机制做增量更新。当用户自上次推荐计算之后的新增互动次数达到3次或以上时，异步触发这个用户的推荐列表重新计算。这样做是为了避免用户当天的偏好变化要等到第二天才能被推荐出来。
相似度矩阵存储
文章相似度矩阵采用稀疏存储：只存相似度大于0.05的文章对（低于这个阈值的就认为不相似）。存储用的是MySQL表article_similarity，字段是article_id_1、article_id_2、similarity_score。在10万篇文章的规模下，预计会存50万到200万条有效的相似度记录。
第3章  需求建模
3.1  业务需求描述
3.1.1 业务背景
本系统的业务逻辑，可以概括成三条相互关联的链条：
个人知识的内化与结构化
用户拿笔记当基本单位，把零散的学习心得、工作备忘和项目资料存进来，用标签和栏目层级做分类索引，再用全文搜索随时找到想要的东西。这条链的核心就是帮个人把外部信息变成自己能搜到、能关联、能再用的内部知识。
团队认知的协同建构
项目文档、会议纪要、需求规格说明书这类需要多人一起写的文本，在CRDT驱动的实时编辑环境里由团队成员一起改。大家能看到彼此的修改痕迹和关注点，让知识成品在集体讨论和反复修改中越变越好，而不是变成某个人的单打独斗。
社区知识的流转与再创作
用户把做好的知识内容以文章形式发到公共区域，其他社区成员通过点赞、收藏、评论这些简单操作表达看法，形成一种去中心化的内容筛选方式。这个发布-反馈-再创作的循环，让隐性知识在社区网络里流动和沉淀下来。
3.1.2 用户角色分析
系统涉及三类用户角色：
普通用户：系统的主要使用者，可进行笔记的创建、编辑、管理、搜索，关注其他用户，参与内容互动。
协作用户：协作用户（系统实际运行中称为注册会员）：在普通用户全部权限基础上，额外具备以下能力：
(1) 创建协作文档并邀请其他注册会员加入编辑；
(2) 接受其他用户的协作邀请，加入其文档的协同编辑；
(3) 使用AI辅助功能（纠错、润色、翻译、扩写、总结、AI小助手）。
协作权限管理
本项目的协作权限采用文档级管理机制：用户对某篇文档的编辑或查看权限，由文档创建者按文档单独授予，而不是基于全局角色来统一分配。具体权限级别定义如下：
owner（创建者）：拥有对该文档的完全控制权，包括编辑内容、管理成员、修改分享权限、删除文档
edit（可编辑）：可实时编辑文档内容，修改会实时同步给所有协作者
view（只读）：仅可查看文档实时内容和其他协作者的光标位置，不可编辑，不可保存
权限数据通过cooperate_member表存储，每条记录关联一个用户和一个协作文档。这个设计把传统的基于全局角色的权限模型，改成了基于文档的细粒度访问控制。这样一来，同一个用户在不同协作文档中可以拥有不同的权限级别。举例来说：用户A对用户B创建的文档X拥有edit权限，但对用户C创建的文档Y只有view权限。
系统管理员
系统管理员负责平台的运营管理，包括用户管理、内容审核、数据统计、轮播图管理等。

3.2  功能需求分析
3.2.1 功能概述
本系统的功能分为四大模块：
核心基础模块
提供内容组织的基础能力，包括栏目管理、标签管理、收藏夹管理、文章搜索、用户信息管理、关注与粉丝管理。

创新功能模块
本项目的两个技术亮点，包括基于CRDT的协同编辑模块和基于大语言模型的AI辅助模块。

第4章  架构设计
4.1  系统架构及原理
4.1.1 整体架构
本系统用的是分层架构，从下到上一共五层：基础设施层、数据层、服务层、应用层和表现层。
基础设施层
就是系统运行的基础环境，包括云服务器、操作系统、Docker容器、网络这些。
数据层
负责数据存盘和管理。MySQL做主数据库，存用户、文章、评论这类结构化数据；Redis做缓存，存会话信息和热点数据；OSS对象存储用来存图片、附件等非结构化数据。
服务层
这是系统的核心业务逻辑层，拆成了四个子服务：
核心业务服务（Java/Spring Boot）：处理用户管理、文章管理、评论管理、搜索等主要业务。同时也当AI网关用，统一接收前端过来的AI请求（纠错、润色、翻译），做完权限校验、敏感词过滤、限流之后，转发给本地的AI辅助服务。
本地AI辅助服务（Python/Flask）：部署在内网的轻量级适配服务，封装了讯飞开放平台的API（纠错、翻译、润色），给核心业务服务提供标准的RESTful接口，负责鉴权封装、响应格式化和结果缓存。
协同服务（Node.js/WebSocket）：基于Yjs处理实时协同编辑的CRDT状态同步。
外部AI辅助服务：前端直接连的第三方服务，包括Elysia Tools（扩写和总结用SSE接口）和讯飞星火大模型（AI小助手用WebSocket接口）。

系统技术架构遵循前后端分离原则，前端与后端通过RESTful API和WebSocket通信。

核心框架：React 18，采用函数式组件和Hooks机制
开发语言：TypeScript，提供静态类型检查
UI组件库：Ant Design 5.x，提供企业级UI组件

路由管理：React Router 6，处理前端路由

后端技术栈：
核心框架：Spring Boot 3.x，提供自动配置和起步依赖

协同服务端：Yjs的y-websocket服务端，处理WebSocket连接和CRDT同步
AI辅助功能技术栈：
核心框架：Flask 2.x，轻量级Web框架
开发语言：Python 3.9+

图4-3 协同编辑时序图
图4-3展示了协同编辑用例的顺序图，描述了多用户实时编辑的交互过程：
建立连接：协作者A打开文档，前端通过WebSocket连接到协同服务，协同服务创建Y.Doc文档实例（如不存在则从数据库加载历史状态）。
加入协作：协作者B通过邀请链接打开同一文档，建立WebSocket连接，协同服务将B加入文档的协作会话。
操作同步：协作者A在编辑器中插入文本，Yjs捕获操作生成Y.Event，通过WebSocket发送到协同服务。
广播更新：协同服务将操作广播给所有连接的协作者（包括B）。
状态合并：各客户端的Yjs根据CRDT算法合并远程操作，更新本地文档状态，编辑器视图同步更新。
光标同步：协同服务通过awareness协议广播用户光标位置和选区，各客户端显示协作者光标。
历史记录：协同服务定期将文档状态持久化到数据库，保存编辑历史。

4.4  数据库设计
4.4.1 概念设计
图4-4 系统ER图
图4-4展示了系统的ER图（实体-关系图），核心实体包括：
用户表（User）
用户ID（id）是主键。其他字段：用户名（username）、密码（password）、年龄（age）、头像URL（avatar）、性别（gender）、个人简介（intro）、邮箱（email）。用户是系统的核心角色，能发布文章、创建专栏、管理标签、进行点赞收藏评论等互动。
文章表（Article）
文章ID（id）是主键。其他字段：发布用户ID（user_id，外键）、发布日期（date）、标题（title）、正文内容（content）、封面图URL（url）、状态（status：0草稿/1待审核/2审核通过/3审核失败）、分类ID（category_id，外键）、专栏ID（column_id，外键）、文章类型（kind：原创/转载/翻译）、摘要（brief）。文章是平台的核心内容，支持发布、编辑、删除、搜索。文章有完整的生命周期：草稿→待审核→审核通过或审核失败。同时支持用户互动（点赞、收藏、评论）和分类管理（专栏、标签、分类）。
专栏表（MyColumn）
专栏ID（id）是主键。其他字段：专栏名称（name）、创建用户ID（user_id，外键）。用户可以建多个专栏来分类管理文章，一篇文章只能属于一个专栏。
标签表（Label）
主键是标签ID（id）。其他字段：标签名称（name）、创建用户ID（user_id，外键）。用户可以建自己的标签，通过关联表和文章做成多对多的关系，方便搜内容和分类。
文章-标签关联表（Article_Label）
主键是关联ID（id）。其他字段：文章ID（article_id，外键）、标签ID（label_id，外键）。这张表是文章和标签的中间表，用来做多对多关联。
评论表（Comment）
主键是评论ID（id）。其他字段：评论日期（date）、文章ID（article_id，外键）、评论内容（content）、评论用户ID（user_id，外键）、父评论ID（parent_id，外键，用来做嵌套回复）、接收者ID（receiver_id）。用户可以对文章发评论，也可以回复别人的评论。
点赞表（Love）
主键是点赞ID（id）。其他字段：用户ID（user_id，外键）、文章ID（article_id，外键）。记录用户点赞了哪篇文章，同一个用户对同一篇文章只能点一次赞。
收藏夹表（Collection）
主键是收藏夹ID（id）。其他字段：用户ID（user_id，外键）、收藏夹名称（name）。用户可以建多个收藏夹，把文章分类收藏起来。
收藏记录实体（Collect）
主键为收藏记录ID（id），属性包括文章ID（article_id，外键）、收藏夹ID（collection_id，外键）、收藏日期（date）、用户ID（user_id，外键）。记录用户将文章收藏到指定收藏夹的行为。
粉丝关注实体（Fans）
主键为关注关系ID（id），属性包括粉丝用户ID（fans_id，外键）、被关注用户ID（user_id，外键）。记录用户之间的关注关系，实现社交关注功能。
收藏记录表（Collect）
主键是收藏记录ID（id）。其他字段：文章ID（article_id，外键）、收藏夹ID（collection_id，外键）、收藏日期（date）、用户ID（user_id，外键）。记录用户把文章收藏到哪个收藏夹。
粉丝关注表（Fans）
主键是关注关系ID（id）。其他字段：粉丝用户ID（fans_id，外键）、被关注用户ID（user_id，外键）。记录用户之间的关注关系，实现社交关注功能。
浏览记录表（Browse）
主键是浏览记录ID（id）。其他字段：用户ID（user_id，外键）、文章ID（article_id，外键）、浏览日期（date）。记录用户看了哪些文章，用来做数据统计和推荐。
私信表（Message）
主键是私信ID（id）。其他字段：发送者ID（sender_id，外键）、接收者ID（receiver_id，外键）、消息内容（content）、发送日期（date）。实现用户之间的私信聊天。
协作文章表（Cooperate_Article）
主键是协作文章ID（id）。其他字段：标题（title）、正文内容（longtext）、创建时间（time）、版本号（version）、保存者ID（saved_by，外键）、创建者ID（created_by，外键），还有status字段（active/archived，表示协作是否还在进行中）。支持多人实时协同编辑，记录版本历史。
Cooperate_Article是独立的协作文档，跟Article完全分开。协作文档不走文章审核流程，也不参与公开内容的互动，只有参与协作的人才能访问。两者设计为独立实体的原因：(1) Article具有发布审核状态机，Cooperate_Article无此需求；(2) Article关联大量社交互动实体（点赞、收藏、评论），Cooperate_Article仅关注编辑协作；(3) Cooperate_Article需要版本快照管理，Article不需要。两者在技术上都属于内容实体，但在业务语义和数据关联上完全不同。
轮播图表（Carousel）
主键是轮播图ID（id）。字段：图片URL（url）。由管理员管理，用来配置首页轮播图。
分类表（Category）
主键是分类ID（id）。字段：分类名称（name）。用来给文章做大类划分。
协作成员表（Cooperate_Member）
主键是记录ID（id）。字段：协作文章ID（article_id，外键连cooperate_article.id）、用户ID（user_id，外键连user.id）、协作角色（role：owner/edit/view）、加入时间（joined_at）。
协作邀请表（Cooperate_Invitation）
主键是邀请ID（id）。字段：协作文章ID（article_id，外键连cooperate_article.id）、邀请者ID（inviter_id，外键连user.id）、被邀请者ID（invitee_id，外键连user.id）、邀请角色（role：edit/view）、邀请状态（status：pending/accepted/rejected/expired）、创建时间（created_at）、过期时间（expires_at）。
AI调用记录表（AI_Call_Log）
主键是记录ID（id）。字段：用户ID（user_id，外键连user.id）、AI功能类型（func_type：polish/translate/expand/correct/summary/chat）、调用路径（call_path：backend_proxy/frontend_direct/frontend_ws）、输入文本长度（input_length）、输出文本长度（output_length）、调用耗时（duration_ms）、HTTP状态码（status_code）、是否命中缓存（cache_hit：0或1）、错误信息（error_msg，可为空）、调用时间（created_at）。索引：(user_id, created_at)和(func_type, created_at)。
文章审核日志表（Article_Audit_Log）
主键是记录ID（id）。其他字段：文章ID（article_id，外键连article.id）、操作管理员ID（admin_id，外键连user.id）、审核前状态（status_before）、审核后状态（status_after：1待审核/2通过/3失败）、审核意见（reason，可为空）、操作时间（created_at）。
通知消息表（Notification）
主键是通知ID（id）。其他字段：接收者用户ID（user_id，外键连user.id）、通知类型（type：like/collect/comment/follow/system）、触发者用户ID（trigger_user_id，外键连user.id）、关联文章ID（article_id，外键连article.id，可为空）、关联评论ID（comment_id，外键连comment.id，可为空）、通知内容摘要（content）、是否已读（is_read：0/1）、创建时间（created_at）。
推荐结果表（Recommend_Result）
主键是记录ID（id）。其他字段：目标用户ID（user_id，外键连user.id）、推荐文章ID列表（article_ids，JSON格式存）、推荐算法类型（algo_type：item_cf/hot/cold_start）、生成时间（created_at）、有效期至（expires_at）。
补充说明：目前系统的推荐逻辑是在Common.java的getRecommendArticles()方法里实时计算的，用的是基于物品的协同过滤（Item-CF）。新增这张表是为了缓存推荐结果，避免每次请求都重复计算，每天凌晨用定时任务更新。

5.2.4 冲突处理机制与实例
本系统用Yjs的YATA算法来保证最终一致性。跟传统的乐观锁或OT算法不一样，CRDT不需要中心服务器来判冲突，而是靠数据结构的设计让并发操作自动合并。下面用两个例子说明。
例子一：两个人同时在同一个位置插入文字
初始状态：文档内容是 "AC"
同时发生的操作：
用户A在A后面插入B
用户B也在A后面插入D
冲突在哪：传统基于索引的方式会出现 insert(1, 'B') 和 insert(1, 'D') 的冲突，没法确定谁先谁后。
CRDT怎么解决：Yjs给每个字符分配一个全局唯一的逻辑ID，由clientId（客户端ID）和递增的clock（逻辑时钟）组成。当两个字符要插到同一个位置时，YATA算法按ID的字典序来决定先后。假设用户A的clientId比用户B小，最终结果可能是"A B D C"或"A D B C"，取决于字典序规则，而且所有客户端会收敛到同一个结果，不需要额外协调。用户A和用户B的操作分别表示为 insert('B', left='A', right='C') 和 insert('D', left='A', right='C')。当操作同步到各个客户端时，YATA算法会按操作ID做确定性排序（比如 O1.ID < O2.ID），所有副本最终一致。结果可能是"ABCD"也可能是"ADBC"，取决于ID大小，但所有客户端看到的结果是一样的。
例子二：同时发生删除和插入（墓碑机制）
初始状态：文档内容是 "Hello World"
同时发生的操作：
用户A删掉 "World"
用户B把 "World" 替换成 "Universe"（先删"World"，再插入"Universe"）
冲突在哪：用户A的删除和用户B的插入是同时进行的。如果直接把字符物理删除，用户B的插入操作就找不到参考位置了。
CRDT怎么解决：Yjs用了墓碑机制。删除操作不会真的把字符从数据结构里删掉，而是给它打个"已删除"的标记。这样用户B的插入操作还能以"World"的位置作为参照。就算"World"已经被标记成了删除状态，它的标识符还留在数据结构里。最后用户B的"Universe"成功插到了原来"World"的位置上，用户A的删除操作让这些字符对用户看不到了，但底层数据还在，能给后面的并发操作提供稳定的参照。两个操作都生效，谁的操作都不会丢。

useEffect(() => {
  if (!quill) return;
  let saveTimer: NodeJS.Timeout;
  const handleChange = () => {
    // 清除之前的定时器
    clearTimeout(saveTimer);
    // 设置新的保存定时器

      const delta = quill.getContents();

  };
}, [quill, docId, user.id]);
5.2.6 Yjs文档状态持久化与恢复机制
协同编辑中，Yjs将文档状态存储在内存中的Y.Doc实例。为确保服务重启或异常断线后数据不丢失，系统设计了以下状态持久化与恢复流程：
1. 定时自动保存（文档快照持久化）：
// 客户端自动保存逻辑（位于src/pages/yjs/components/quill/index.tsx）
// Saver选举算法：所有在线用户中ID最小者承担自动保存职责
const electSaver = () => {
  const onlineUserIds = [...awareness.getStates().values()]
    .map(s => s.user?.id)
    .filter(Boolean)
    .sort((a, b) => a - b);
  return onlineUserIds[0]; // 最小ID用户为saver
};
// 仅当选的saver执行周期性保存
useEffect(() => {
  const interval = setInterval(async () => {
    const currentSaverId = electSaver();
    if (currentSaverId !== user.id) return; // 非saver跳过
    const ytext = ydoc.getText("quill");
    const content = ytext.toString(); // Y.Text → 纯文本
    await saveCooperateArticleAPI({
      id: docId,
      content: content,
      version: dayjs().format("YYYY/MM/DD HH:mm:ss"),
      savedBy: user.id,
    });
  }, 30000); // 每30秒检查一次
  return () => clearInterval(interval);
}, [ydoc, docId, user.id]);
2. Yjs服务端状态恢复：
// 服务端（Node.js y-websocket）启动时从数据库加载文档状态
// 伪代码描述y-websocket服务端持久化逻辑
const persistence = {
  // 从MySQL加载文档初始状态
  async bindState(docName, ydoc) {
    const row = await db.query(
      "SELECT content FROM cooperate_article WHERE id = ?", [docName]
    );
    if (row) {
      // 将数据库中的内容恢复到Y.Doc
      const ytext = ydoc.getText("quill");
      ytext.insert(0, row.content);
    }
    // 监听Y.Doc更新，定期持久化
    ydoc.on("update", debounce(async (update) => {
      const content = ydoc.getText("quill").toString();
      await db.query(
        "UPDATE cooperate_article SET content = ? WHERE id = ?",
        [content, docName]
      );
    }, 2000)); // 2秒防抖，避免频繁写入
  },
  // 写入版本快照
  async writeState(docName, ydoc) {
    const content = ydoc.getText("quill").toString();
    // 获取当前最大revision_no并+1
    const [row] = await db.query(
      "SELECT MAX(revision_no) as max_rev FROM cooperate_article_revision WHERE article_id = ?",
      [docName]
    );
    const nextRev = (row.max_rev || 0) + 1;
    await db.query(
      `INSERT INTO cooperate_article_revision
       (article_id, revision_no, title, content, editor_id, created_at)
       VALUES (?, ?, ?, ?, ?, NOW())`,
      [docName, nextRev, null, content, null]
    );
  },
};
5.3  AI辅助模块
5.3.1 模块概述
AI 辅助模块为博客写作/协作编辑提供两类能力：AI 对话助手与文本智能处理（润色/翻译/扩写/纠错/总结）。实现上主要集中在前端 myBlog，通过调用本地 AI 服务（http://localhost:5000）以及第三方 SSE 流式接口完成能力编排，并在协作编辑页中把 AI 结果回填到 Quill 富文本编辑器。
AI 对话助手：页面悬浮聊天窗口，WebSocket 方式获取大模型流式回复（先 GET 获取 ws URL，再建立 ws 连接并持续接收分片更新）。代码位于 myBlog/src/pages/chat/index.tsx（AIChatService 负责连接与消息队列）以及 myBlog/src/apis/ws.ts（获取 ws url）。
图5-8 AI对话助手时序图
这个流程图画的是AI聊天助手的完整流程：
用户打开页面后，系统初始化AIChat组件，建一个WebSocket连接。用户发消息时，系统先把消息加到队列里，同时加一条AI的占位消息。如果WebSocket还没连上，就先连一下；连上之后，构造一个包含系统提示词、历史消息和当前输入的请求，发给后端。收到返回的消息后，系统把文本分片一段一段追加到AI消息里，实时刷新聊天窗口，直到连接关掉或出异常。
文本智能处理
统一入口是convert(type, text, setContent)，根据类型走不同的通道
润色（改写）：POST /text/rewrite
翻译：POST /text/translate
纠错：POST /text/correction
扩写/总结：通过SSEService连第三方工具站点，流式接收分片，边收边拼边刷新界面
图5-9 AI文本智能处理时序图
这个时序图画的是AI辅助功能的调用流程：
用户选中一段文字后，前端根据选的是什么功能来分流处理。如果是润色、翻译或纠错，就调用本地AI辅助功能的HTTP接口；如果是扩写或总结，就建立SSE连接，流式接收返回的数据块。拿到结果后先做Markdown渲染，再展示给用户，用户确认没问题之后可以替换掉编辑器里原来选中的文字。

AI对话：
async connect(): Promise<boolean> {
  if (this.ws?.readyState === WebSocket.OPEN) return true;
  if (this.isConnecting) return false;
  this.isConnecting = true;
  const res = await getWsUrlAPI();
  const url = res.data;
  return new Promise((resolve) => {
    this.ws = new WebSocket(url);
    this.ws.onopen = () => {
      this.isConnecting = false;
      this.reconnectAttempts = 0;
      this.onConnectionChange?.(true);
      resolve(true);
    };
    this.ws.onmessage = (event) => {
      const data = JSON.parse(event.data);
      if (data.payload?.choices?.text?.[0]?.content) {
        const chunk = data.payload.choices.text[0].content;
        const i = this.messageQueue.length - 1;
        if (i >= 0 && this.messageQueue[i].author === "ai") this.messageQueue[i].data.text += chunk;
        else this.messageQueue.push({ type: "text", author: "ai", data: { text: chunk } });
        this.notifyMessageUpdate();
      }
    };
  });
}

const handleSendMessage = async (content: string) => {
  if (!content.trim()) return;
  const message: Message = {
    id: null,
    senderId: user.id,
    receiverId: selectedFriend.id,
    content: content,
    date: new Date()
  };

  // 2. 发送到服务器

第7章 结  论
7.1  工作总结
本项目按照“需求分析→架构设计→模块实现→系统测试”这个工程流程，完成了融合协同编辑和大模型辅助的智能云笔记系统的全栈开发。主要成果有五个方面：
1. 需求梳理和架构设计
用用例驱动的方法把功能需求理了一遍。以前后端分离和AI微服务化两条主线，设计了技术架构的分层结构，给后面的开发定了方向。
2. 云笔记基础功能全部做完
实现了用户登录认证、栏目-标签两级分类、文章从草稿到发布到归档的状态流转、全文搜索、社交互动（点赞、收藏、评论、关注）这些个人知识管理需要的基础功能。
3. CRDT实时协同编辑
用Yjs的YATA算法和y-websocket，搭了一个多人同时编辑的无锁同步通道。系统支持操作增量的确定性广播和自动解决冲突、光标位置的实时感知、自动快照保存，以及版本历史的全量查看和自动裁剪。
4. 大模型AI辅助功能接入
按照安全等级和延迟要求做了分流，把语法校对、润色、翻译、扩写、摘要这五个AI功能，通过后端代理和前端直连两条路径集成到编辑流程里。既提升了文档质量，又保证了密钥安全和流式体验。
5. 测试验证和容器化部署
用JMeter在100个用户并发下测了系统的吞吐量、延迟和错误率；在Chrome、Firefox、Edge、Safari四个浏览器上验证了界面一致性；用Docker Compose实现了整套服务的一键部署。
7.2  存在的不足
（1）AI功能依赖外部API且审计不完整
当前纠错、翻译、润色功能依赖讯飞开放平台API，扩写、总结功能依赖Elysia Tools API，AI小助手依赖讯飞星火大模型WebSocket接口。三类外部API存在网络延迟波动（AI纠错未命中缓存时P99延迟达2100ms）、服务稳定性不可控（第三方故障时只能降级提示"服务繁忙"）、调用成本随用户量增长而线性增加等问题。同时，AI_Call_Log审计表已完成数据库设计但尚未集成到实际调用链路中，无法追踪每次AI调用的输入长度、耗时、缓存命中率和异常情况，对异常调用模式的检测能力不足。
（2）协同编辑离线支持与回滚功能有限
CRDT算法理论上本来就支持离线编辑（本地操作等网络恢复了之后可以自动合并），但我们现在这个实现里，Yjs文档状态的持久化还得靠中心化的MySQL数据库，服务端是通过y-websocket的update事件来同步内容的。如果网络断的时间比较长，超过了y-websocket的update日志缓冲区大小，重连之后增量同步可能会因为update日志缺失导致状态对不上。
还有一个问题是版本回滚。目前只能“预览历史版本”，还没法“一键恢复到任意历史版本”。虽然cooperate_article_revision表已经记录了每次保存的快照，并且自动限制了最多存50条，但恢复功能还没做全。
（3）搜索功能缺乏语义理解能力
目前文章搜索用的是MySQL的LIKE模糊匹配，只能按关键词的字面意思去找。这种办法理解不了用户真正想查什么。比如用户搜“如何提升代码质量”，系统没法把一篇标题叫“软件工程最佳实践”但内容里讲了代码质量的文章推出来。而且搜索结果排序只看发布日期，没有根据相关性来排。
（4）推荐算法缺乏工程化验证
系统在Common.java里实现了一个基于物品协同过滤（Item-CF）的推荐算法原型，用用户的历史点赞行为来算文章相似度，然后生成推荐列表。但这个实现有三个工程上的问题：
第一，没有离线评估体系。准确率、召回率、覆盖率这些指标没有定期计算和跟踪。
第二，没有A/B测试框架。没法对比Item-CF算法和热门推荐基线（也就是现在的冷启动策略）哪个效果更好。
第三，推荐结果每次请求都要实时算，没有用recommend_result缓存表来做预计算和定时刷新。
7.3  后续改进方向
（1）完善协同编辑体系
把CRDT版本回滚功能做完整
用Yjs的snapshot机制和现有的cooperate_article_revision表，在版本预览页面加一个“恢复到此版本”的按钮。后端创建新快照（revision_no递增）来记录回滚操作，前端重新加载Y.Doc状态。
增加文档内评论标注功能
协作者可以对文档的某一段落加批注（用Quill的format API标记范围），批注数据存到新建的cooperate_annotation表里。
完善WebSocket鉴权
目前y-websocket服务端还没做JWT验证，需要在连接upgrade阶段从URL参数里解析token，校验用户身份之后，再查cooperate_member表做文档级的权限控制。
（2）完善AI安全与审计
集成三条AI调用路径都加上日志
把AI_Call_Log表集成到三条AI调用路径里：
后端代理路径：在Python Flask服务的每个API入口记录调用日志
前端直连路径：前端在建立SSE或WebSocket连接时，发一个埋点请求到后端记录日志
前端WebSocket路径：同样用埋点请求记录日志
用Redis做滑动窗口限流
基于Redis实现用户级和IP级的滑动窗口限流：
用户级：每分钟每个用户最多调纠错、润色、翻译各10次，扩写、总结各5次
IP级：每分钟每个IP最多调20次
加异常调用检测
如果某个用户在1小时内的AI调用次数超过了平均值的3个标准差，就触发告警。
（3）增强推荐系统
建立离线评估体系
每周计算Item-CF算法在最近7天测试数据上的准确率（推荐5篇中用户产生互动的比例）、召回率（用户实际互动的文章中被推荐的比例）和覆盖率（被推荐过的去重文章占总文章的比例），与热门推荐基线对比。
做一个简化的A/B测试
在首页推荐位随机展示两种推荐结果：一半的用户看到Item-CF推荐的，另一半看到热门推荐的。通过浏览记录里存的article_id来源来区分这两组，每周统计一下两组用户的平均互动次数，看看哪个效果更好。
定时预计算推荐结果
用Spring的@Scheduled注解写一个定时任务，每天凌晨2:00跑一次，调用Common.getRecommendArticles()给活跃用户预计算推荐列表，然后存到recommend_result缓存表里。前端要推荐的时候优先读缓存，不用每次都实时算了。
（4）引入语义搜索能力
在MySQL全文搜索的基础上，引入向量检索技术作为增强：使用开源的text2vec-base-chinese模型将文章内容转换为768维向量存储在新增的article_embedding表中，用户搜索时将查询语句同样转为向量，通过余弦相似度计算返回语义最相关的前20篇文章，再结合MySQL的LIKE结果取并集，提升搜索的召回率和语义理解能力。
